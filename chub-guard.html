chub-guard: catching outdated AI code before it ships

AI SDKs change faster than linters, and faster than the coding assistants that write against them. chub-guard is a linter whose rules aren't written by hand: it reads each library's current documentation and flags the calls that documentation says are gone.

01The problem

Ask a coding assistant for an OpenAI call and there's a fair chance you get this:

import openai

resp = openai.ChatCompletion.create(model="gpt-4o-mini", messages=msgs)

That call was removed in version 1.0 of the SDK. It looks right, a syntax linter passes it, and it fails the first time it runs. The same thing happens with Gemini's old google.generativeai package, Anthropic's legacy text completions and LangChain's pre-1.0 chains. Linters like Ruff and ESLint know a language's rules; they don't know that a library dropped a function last quarter.

Hand-writing a rule for every deprecation in every AI SDK doesn't scale, and it would always be a release behind. I wanted the rules to come from somewhere that's already kept current.

02How it works

The libraries' own documentation already says what's deprecated. Context Hub publishes that documentation in a form written for LLMs, one Markdown file per library. chub-guard turns those files into lint rules at run time.

  1. Find what the code importsPython is parsed with the ast module; JavaScript, TypeScript, Java and C/C++ imports are read with patterns.
  2. Map each import to its documentationA registry links module names to Context Hub docs, including aliases such as @anthropic-ai/sdk. Imports with no docs are skipped quietly.
  3. Fetch the current docsThrough the chub CLI, or straight from GitHub if it isn't installed. Cached for 24 hours; a network failure warns but never blocks a commit.
  4. Extract what the docs call deprecatedLines that warn against something, "Migration" and "Deprecated" sections, and ❌ counter-examples. A shared pattern file, synced daily, adds what earlier runs found.
  5. Flag the lines that use itWith the modern replacement quoted from the same docs, a severity, and a prompt an AI assistant can use to fix every issue in one pass.

Decisions that mattered

  • It doesn't give up on files that don't parse. A Python 2 file, or one that's mid-refactor, falls back to a pattern-only pass instead of being skipped. Those are the files most likely to hold old calls.
  • It meets people where they already are. The same engine runs as a VS Code extension (squiggles as you type), a pre-commit hook (the commit is blocked) and a CLI (a full-project report with trends).
  • It can be overruled. # noqa: CHUB on a line silences it, in every language.
  • One command to set up. npx chub-guard-init installs the hook and the registry in an existing project.

03What it got wrong

Building the live playground for this site meant running chub-guard on code I hadn't written the examples for. It flagged this, which is correct, current Anthropic code:

message = client.messages.create(model="claude-sonnet-4-5", max_tokens=1024, messages=msgs)
print(message.content[0].text)   # flagged: `message.content` is deprecated

The cause was one line in Anthropic's docs: "Do not treat message.content as a single string." chub-guard 1.2.1 reads any name mentioned near a warning word as deprecated. That sentence is advice about how to use a current call, not a deprecation, and the same docs use message.content in every example.

It wasn't a one-off. The same thing flagged client.chat.completions.create (OpenAI's current chat call) and response.text (Gemini). In JavaScript it was worse: patterns were split into single words, so client and create were flagged wherever they appeared.

A linter that cries wolf on correct code gets switched off, so this mattered more than a missed deprecation would have.

04The fix, and how I measured it

The docs that caused the problem also held the answer. If a library's own current examples use a call, it isn't deprecated, whatever a nearby sentence says. So before flagging anything, the check now collects what each doc presents as current (its example code outside "Deprecated" sections and ❌ blocks, and names on lines that don't warn against anything) and drops any pattern found there. In JavaScript, only class-like names from a deprecated pattern are matched, as whole words.

To know whether that helped or just moved the problem, I wrote a small benchmark: 13 snippets, 74 lines, with the 19 lines that really use something deprecated labelled by hand. Six snippets are old code that should be flagged; seven are current code that shouldn't be. Both rule sets run against the live docs.

Recall stayed at 18 of 19 (95%). My first version of the fix actually lost one: it judged the docs line by line, and Gemini's warning about retired models wraps onto a second line, so gemini-1.5-flash was read as current. Judging a whole sentence or list item at a time brought it back. The benchmark caught that before anyone else did, which is the reason to have one.

The one line both versions miss is genai.configure(api_key="..."). The docs write the old call with a placeholder, genai.configure(api_key=...), and the match is on exact text.

What this does and doesn't show: 13 snippets is a small set, chosen by me, of the libraries chub-guard is used with most. It's enough to catch a regression and to compare two rule sets; it isn't a claim about every codebase. It's in this site's repository and runs with npm run bench. The fix runs in the playground on this site today, and goes into the next release of the CLI.

05What I'd do next

  • Ship the current-usage rule in the CLI and the extension, with the benchmark as a test that has to pass before a release.
  • Match placeholders, so f(x=...) in the docs matches f(x="anything") in code. That's the one miss above.
  • Grow the benchmark from real repositories, not snippets I wrote, and track precision and recall for each library separately.
  • Say why. Each flag should quote the sentence in the docs it came from, so a wrong one is obvious at a glance.
